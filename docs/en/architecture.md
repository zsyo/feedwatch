## Project Layout

```
.github/workflows/docker-publish.yml  tag-triggered GHCR dual-group dual-arch publish (matrix: base / webui)
Dockerfile / Dockerfile.webui  base two-stage build / webui build with an extra Node frontend stage
docker-compose.yml / docker-compose.webui.yml  base / webui deployment (run one or the other)
cmd/feedwatch/main.go          only composition root; a very thin hook forks to the webui variant after -version
internal/domain/              domain models (zero internal dependencies)
internal/config/               YAML + env overrides + validation
internal/source/               Source interface / Registry
internal/source/atom/          Atom/RSS parsing, conditional requests, retries
internal/source/github/        GitHub Releases REST fetching + optional GraphQL batch prefetch
internal/filter/               stable-version filter rules
internal/notifier/             Notifier interface / Registry / Multi fan-out & failure policy / delivery pacing decorator
internal/notifier/template/    go:embed email & IM message templates (shared by baseline / new-version)
internal/notifier/email/       Resend implementation
internal/notifier/log/         log notifier (local debugging / dry-run)
internal/notifier/webhook/     shared HTTP engine + 10 channel Adapters (one file per channel)
internal/pace/                 bounded concurrency + minimum-interval gates (one global for fetching, one per channel type for delivery)
internal/store/                StateStore interface / Registry
internal/store/jsonfile/       atomic JSON state writes + startup writability probe
internal/watcher/              base core orchestration: bounded concurrent fetch → filter → diff → batched notify → commit per batch (webui leaves it untouched)
internal/webui/                WebUI variant (all //go:build webui): first-start admin seed, channel field spec, URL normalization, embedded assets
internal/webui/catalogspec.go  catalog field limits, URL safety checks, built-in examples, import/export structs (single Go-side source of truth)
internal/webui/secrets/        master key loading + AES-256-GCM envelope encryption (the only package that knows the key)
internal/webui/store/          connection & dialect layer (SQLite / MySQL / PostgreSQL), three DDL files, migration version table, WAL & directory writability probe (schema v8)
internal/webui/auth/           bcrypt passwords, session, CSRF
internal/webui/oauth/          GitHub / linux.do authorization-code flow (authorize URL, token exchange, identity, state & PKCE generation; no DB access)
internal/webui/presets/        remote preset JSON validation, loader and SSRF protection (pure functions + network, no DB access)
internal/webui/api/            HTTP server, middleware chain, /api/* endpoints and SPA static serving; catalog.go / catalog_admin.go / catalog_presets.go cover the catalog & remote sync, auth_register.go / auth_oauth.go cover self-registration & third-party login
internal/webui/orchestrator/   multi-tenant polling: URL dedup pool, per-user policy routing, independent delivery & per-channel-type pacing
internal/webui/embedded/       only stub.html / .gitkeep are committed; real assets are generated by the build and gitignored
web/                          Vue 3 + Vite + TS sources; CatalogView / CatalogPendingView, 5 AdminCatalog* sub-page Views, RegisterView / AdminAuthView, catalogAdmin.ts / presets.ts / authMeta.ts plus build.sh / build.ps1
presets/                      remote preset data: manifest.json + 4 category JSON files (read remotely at run time, not baked into the image)
testdata/                     test feed fixtures
```

The base binary links only two external modules: `go.yaml.in/yaml/v4` and `github.com/resend/resend-go/v4`; the `-tags webui` variant additionally links `modernc.org/sqlite`, `github.com/go-sql-driver/mysql`, `github.com/jackc/pgx/v5` (all pure Go, no cgo) and `golang.org/x/crypto/bcrypt`. `go.mod` lists all of them, but the linker strips WebUI dependencies out of the base binary. Atom parsing uses the standard library's `encoding/xml`.

> Why this YAML dependency: the original `gopkg.in/yaml.v3` (`go-yaml/yaml`) was marked unmaintained by its author in April 2025; the official YAML organization's successor is `go.yaml.in/yaml/*`, where v3 is a frozen API (security fixes only) and **v4 is the actively maintained stable release** — hence this project uses v4 directly. `github.com/goccy/go-yaml` is an unrelated from-scratch rewrite, not the official successor, and is not used here. Config parsing still uses the classic `Unmarshal` API for stable behavior; the `Node` in the two custom `UnmarshalYAML(*yaml.Node)` hooks must come from the same module, otherwise v4 reports a migration error.

## How to Extend

**Add a data source**: create `internal/source/<name>/`, implement `source.Source` (`Type()` + `Fetch(ctx, Cursor) (Result, error)`), export a `New` matching `source.Factory`, and add one `srcReg.Register(...)` line in each of `main.go` and `webui_hook_webui.go`; add the corresponding `type` in config / UI. New parameters pass through `feeds[].options`. `domain` / `config` / `filter` / `store` / `notifier` / `watcher` / templates / both Dockerfiles **need no changes** (both builds reuse the same leaf packages). `internal/source/github/` is a complete example: REST primary path + optional GraphQL batch (per-round cache injected via context, falling back to REST per repository on failure).

**Add a notification channel** (e.g. Matrix): add a file in `internal/notifier/webhook/` implementing `webhook.Adapter` (`Type()` + `Build(Message, Options) (Request, error)` + `Check(status, body) error`) and one line in `Adapters()` in `webhook/adapters.go`. The HTTP client, retry/backoff, rendering, logging and secret expansion all live in the shared engine, so `main.go` / `config` / `watcher` / templates / both Dockerfiles (base / webui) **need no changes** (both builds reuse the same leaf packages); just write `type: matrix` + `options` in the config, and it can coexist with existing channels.

If a new channel is not HTTP-based at all (e.g. writing to a database, publishing MQTT), create a separate package implementing `notifier.Notifier` and add one line in `main.go`: `notifReg.Register("xxx", xxx.New)` — `notify.channels` will automatically include it in the fan-out.

**Add a state store** (e.g. SQLite): implement `store.StateStore` (`Load` returns `store.ErrNotFound` for a first run), register it and change `store.type`. Note that the WebUI variant's SQLite is a separate multi-tenant store (`internal/webui/store/`) and does not use this interface.
